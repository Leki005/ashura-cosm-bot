## 1. Race Condition: Двойное создание записи при быстром двойном клике

| | |
|:---|:---|
| **Файл** | `handlers/client.py` |
| **Строка** | `_finalize_booking`, ~строка 365-375 |
| **Что не так** | `await state.clear()` вызывается **после** чтения данных из state, но **до** проверки `get_active_booking`. Если пользователь быстро кликнет дважды (или нажмёт Enter + кнопку), оба запроса прочитают `state.get_data()`, найдут его валидным, и оба пройдут проверку `get_active_booking` до того, как любой из них создаст запись. |
| **Исправление** | Использовать паттерн "check-then-set" с атомарной операцией в БД, или установить флаг в state **до** проверки: |

```python
# В начале _finalize_booking:
data = await state.get_data()
if data.get("_finalizing"):
    return  # Уже финализируется
await state.update_data(_finalizing=True)

# Или лучше — использовать SELECT FOR UPDATE в БД:
existing_active = await session.execute(
    select(Booking)
    .where(Booking.user_id == user.id)
    .where(Booking.status.in_(ACTIVE_BOOKING_STATUSES))
    .with_for_update()  # Блокирует строку
)
```

## 2. Race Condition: Некорректная проверка бонусов (TOCTOU)

| | |
|:---|:---|
| **Файл** | `handlers/client.py` |
| **Строка** | ~строка 380-395 |
| **Что не так** | Сначала читается `user.bonus_balance` для расчёта `max_discount`, затем делается `UPDATE ... WHERE bonus_balance >= bonus_used`. Но между этими операциями другой запрос может изменить баланс. Проверка `result.rowcount == 0` — это лучше, чем ничего, но не решает проблему перерасчёта `max_discount` на устаревших данных. |
| **Исправление** | Перенести всю логику расчёта в один атомарный запрос, или использовать `SELECT FOR UPDATE` при чтении пользователя: |

```python
# В начале транзакции:
result = await session.execute(
    select(User).where(User.id == user.id).with_for_update()
)
user = result.scalar_one()

# Затем расчёт на актуальных данных и UPDATE без условия,
# или с условием но с пересчитанным значением
```

## 3. Утечка памяти: Неограниченный рост `_error_tasks`

| | |
|:---|:---|
| **Файл** | `bot.py` |
| **Строка** | ~строка 60-70 |
| **Что не так** | `_error_tasks: set[asyncio.Task] = set()` — задачи добавляются, но при `add_done_callback` они удаляются только если **успешно завершились**. Если задача застряла (например, сетевая ошибка при отправке в Telegram), `add_done_callback` не вызовется, и задача останется в сете навсегда. Кроме того, `_ERROR_TASKS_MAX` защищает от добавления, но не от утечки "зависших" задач. |
| **Исправление** | Использовать `weakref` или периодическую очистку, или проще — не хранить задачи вообще, если не нужен `await`: |

```python
# Вариант 1: fire-and-forget с обёрткой
async def _fire_and_forget(coro):
    try:
        await coro
    except Exception:
        pass

# В emit:
loop = asyncio.get_running_loop()
loop.create_task(_fire_and_forget(notify_error(...)))
# Не храним ссылку вообще

# Вариант 2: Если нужен трекинг — periodic cleanup:
async def _cleanup_error_tasks():
    stale = [t for t in _error_tasks if t.done()]
    for t in stale:
        _error_tasks.discard(t)
```

## 4. SQL Injection в миграциях через f-string

| | |
|:---|:---|
| **Файл** | `database.py` |
| **Строка** | `apply_migrations`, ~строка 310-330 и далее |
| **Что не так** | `await session.execute(text(f"ALTER TABLE {table} ADD COLUMN {column} ..."))` — хотя `table` и `column` контролируются кодом, это плохая практика. Если в будущем эти значения будут приходить извне (например, из конфига), будет SQLi. |
| **Исправление** | Использовать параметризацию или хотя бы `sqlalchemy` DDL: |

```python
from sqlalchemy import Column, Text, Boolean, DateTime
from sqlalchemy.schema import AddConstraint, CreateColumn

# Или минимально — quote_ident:
from sqlalchemy import text
safe_table = table  # validate against whitelist
safe_column = column
await session.execute(
    text(f'ALTER TABLE "{safe_table}" ADD COLUMN "{safe_column}" TEXT')
)
# Но лучше полностью перейти на Alembic для миграций
```

## 5. Race Condition: Напоминания шедулера без блокировки

| | |
|:---|:---|
| **Файл** | `bot.py` |
| **Строка** | `send_reminders`, ~строка 240-280 |
| **Что не так** | Шедулер запускается каждые 5 минут. Если предыдущий запуск не успел завершиться (например, при медленной сети), начинается новый. Обе корутины читают `reminder_24h_sent = False`, обе отправляют напоминание, обе делают `session.flush()`. Вторая перезапишет первую, но клиент получит два сообщения. |
| **Исправление** | Добавить `replace_existing=True` в шедулер (уже есть) + использовать `with_for_update()` при выборке записей, или отслеживать "in-flight" напоминания: |

```python
# Глобальный сет или лучше — поле в БД:
# reminder_24h_sent = 'sending'  -- промежуточное состояние

# Или в шедулере:
scheduler.add_job(
    send_reminders,
    "interval",
    minutes=5,
    max_instances=1,  # Критично! Не запускать параллельно
    ...
)
```

## 6. Утечка сессии БД в middleware + неотловленные исключения

| | |
|:---|:---|
| **Файл** | `bot.py` |
| **Строка** | `DbSessionMiddleware.__call__`, ~строка 140-155 |
| **Что не так** | Если `handler` выбрасывает исключение, `session.rollback()` вызывается, но `session` не закрывается явно. `async with` должен закрыть, но если исключение произошло в `session.commit()` (например, deadlock), `async with` может не отработать корректно. Также `session.commit()` после handler — опасно: если handler делал `flush()`, а потом другая операция упала, частичные данные уже в БД. |
| **Исправление** | Явно разделить read-only и write сценарии, или использовать `begin()` для автоматического коммита/отката: |

```python
async def __call__(self, handler, event, data):
    async with async_session() as session:
        async with session.begin():  # Автоматический commit/rollback
            data["session"] = session
            try:
                result = await handler(event, data)
                return result
            except Exception:
                # session.begin() автоматически откатит при выходе из контекста
                raise
```

## 7. Потеря данных: `session.commit()` в middleware после любого handler'а

| | |
|:---|:---|
| **Файл** | `bot.py` |
| **Строка** | `DbSessionMiddleware`, ~строка 149 |
| **Что не так** | Коммитится **любое** изменение, даже если handler просто читал данные. Это создаёт риск случайного коммита "грязных" данных, если handler где-то в глубине изменил объект и забыл. Также это неявное поведение, нарушающее принцип наименьшего удивления. |
| **Исправление** | Убрать автоматический `commit` из middleware. Хендлеры, которым нужна запись, должны явно коммитить: |

```python
# В middleware:
# Убрать await session.commit()

# В хендлерах, которые пишут:
await session.commit()  # Явно, там где нужно
```

Или использовать паттерн "unit of work" с явным флагом.

## 8. Утечка памяти: `_grok_session` без TTL и без cleanup при ошибках

| | |
|:---|:---|
| **Файл** | `utils/grok.py` |
| **Строка** | `_get_http_session`, ~строка 85-110 |
| **Что не так** | Сессия создаётся один раз и живёт вечно. При смене прокси старая закрывается, но если прокси падает/меняется часто, создаются новые TCP-коннекторы. `ClientSession` держит внутренний коннектор-пул, который при долгой работе может накапливать "зомби"-соединения. Также при `KeyboardInterrupt` или `SystemExit` сессия не закрывается. |
| **Исправление** | Добавить TTL для сессии, пересоздавать каждые N часов, и использовать `weakref.finalize` или `atexit`: |

```python
import weakref
import atexit

_session_created_at: float = 0
_SESSION_TTL_SECONDS = 3600  # 1 час

async def _get_http_session(proxy_url: str | None) -> ClientSession:
    global _grok_session, _grok_session_proxy, _session_created_at
    now = asyncio.get_event_loop().time()
    
    needs_new = (
        _grok_session is None 
        or _grok_session.closed
        or _grok_session_proxy != proxy_url
        or (now - _session_created_at) > _SESSION_TTL_SECONDS
    )
    
    if needs_new and _grok_session is not None and not _grok_session.closed:
        await _grok_session.close()
        # Дать время на закрытие TCP-соединений
        await asyncio.sleep(0.1)
    
    if needs_new:
        # ... create new ...
        _session_created_at = now

# Гарантированный cleanup:
def _cleanup_grok():
    if _grok_session is not None and not _grok_session.closed:
        asyncio.get_event_loop().run_until_complete(_grok_session.close())

atexit.register(_cleanup_grok)
```

## 9. Небезопасная десериализация: `json.loads` без валидации схемы

| | |
|:---|:---|
| **Файл** | `utils/helpers.py` |
| **Строка** | `parse_extra_services`, `format_skin_anamnesis`, `format_anamnesis` и др. |
| **Что не так** | `json.loads()` на данных из БД без валидации. Если данные повреждены или злоумышленно изменены (через админку или если есть инъекция в другом месте), код упадёт с `KeyError`, `TypeError` или хуже. Например, `data.get('problems', [])` ожидает список, но может прийти строка. |
| **Исправление** | Использовать `pydantic` для валидации, или минимально — defensive programming: |

```python
from pydantic import BaseModel, validator
from typing import Literal, List

class SkinAnamnesis(BaseModel):
    skin_type: Literal["oily", "dry", "combo", "normal", "sensitive"] | None = None
    problems: List[str] = []
    
    @validator('problems', pre=True)
    def ensure_list(cls, v):
        if isinstance(v, str):
            return [v] if v else []
        return v if isinstance(v, list) else []

# Использование:
try:
    data = SkinAnamnesis.parse_raw(skin_json)
except ValidationError:
    logger.error("Invalid skin anamnesis data")
    return "⚠️ Ошибка в данных анкеза"
```

## 10. Утечка памяти: `_last_message_time` в throttling без bound + не thread-safe

| | |
|:---|:---|
| **Файл** | `utils/helpers.py` |
| **Строка** | `check_throttle`, ~строка 50-85 |
| **Что не так** | Глобальный `dict` без ограничения по времени жизни записей. "Периодическая очистка" работает только при **новом** вызове — если бот долго не получает сообщений, старые записи висят вечно. Также `del _last_message_time[uid]` внутри list comprehension создаёт копию, но сама очистка — O(n²) из-за `sorted`. Нет защиты от negative timestamp (clock skew). |
| **Исправление** | Использовать `TTLCache` из `cachetools` или `expiringdict`, или реализовать правильную очистку: |

```python
from collections import OrderedDict
import time

class ThrottleCache:
    def __init__(self, ttl: float, max_size: int = 10000):
        self._data: OrderedDict[int, float] = OrderedDict()
        self._ttl = ttl
        self._max_size = max_size
    
    def check(self, user_id: int) -> bool:
        now = time.time()
        # Cleanup old entries from the left (oldest)
        while self._data and next(iter(self._data.values())) < now - self._ttl:
            self._data.popitem(last=False)
        
        # Check limit
        if user_id in self._data:
            if now - self._data[user_id] < self._ttl:
                return True  # Throttled
        
        # Add/update
        self._data[user_id] = now
        if len(self._data) > self._max_size:
            self._data.popitem(last=False)
        return False

# Глобальный instance:
_throttle_cache = ThrottleCache(ttl=Config.THROTTLE_RATE)

async def check_throttle(user_id: int) -> bool:
    return _throttle_cache.check(user_id)
```
